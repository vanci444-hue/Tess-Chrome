01 / 从观察到切口建议 4 分钟

试驾结束了，判断还没有结束。

一手观察 · 单次体验

离店后，需要自己重新复盘

在我的这次体验中，离店时没有收到整合后的试驾复盘，需要主动索取配置截图。哪些方案值得继续比较、哪些问题已明确，仍需自己整理。

用户转述 · 未推广为普遍结论

销售也表达了报告需求

据我的沟通记录，销售表达过对个性化配置报告的期待。这支持继续验证该需求，但不代表其他销售的普遍意愿或真实采用率。

客户带走的不只是配置和报价，还应包括：正在比较什么、已经确认什么、还有什么值得确认。

由此提出的假设：试驾后的共同记录，可能减少客户重复整理和销售重复解释，让后续沟通围绕具体未决事项展开。

为什么先做这个切口：它靠近真实购车决策，有清晰的销售输入和客户输出，也能在不接入内部 CRM 的作业范围内验证关键体验。没有内部漏斗数据，目前不能判断它是最大流失点或最高价值场景。

研究边界与完整推导

公开资料与个人体验用于提出假设；需要更多销售、用户访谈和内部数据验证。观察到销售使用内部工具，不等于了解 Tesla 的内网架构、系统覆盖或流程缺陷。

02 / 产品定义建议 3 分钟

销售侧做事，客户侧看清结果。

销售侧 · Chrome Side Panel

依次进入客户、试驾会话和对话。先明确客户归属，再抓取官网选配；支持粘贴 CRM 必要信息和语音补充。实时字幕可修改，必须手动发送。

Agent 根据本次背景准备信息和报告，销售确认疑点并审核后生成链接。

客户侧 · 桌面 Report

首屏回答三个决策问题；再展示方案、金融、充电与能源成本。图表保留单位、计算假设、来源与时间，未知数据不补零。

本次链接在演示电脑打开。Ask Tess、分享、联系等按钮为静态展示；有有效结果时，地图可链接到高德继续搜索。

本次取舍

只支持 Tesla 中国 Model Y 配置器；销售身份为模拟已登录。内部 CRM / 金融接口使用明确标记的 Mock，真实官网快照不能被 Mock 覆盖。

保留必要控制

同一客户可有多次会话。报告发布前审核，发布后内容固定；不做复杂版本对比。价格和计算结果通过重新采集、修改输入后重算来纠正。

后续产品愿景

家庭成员继续提问、顾虑回传销售，形成持续跟进闭环。本次仅以模拟事件展示销售侧摘要，不代表真实家庭问答已上线。

待验证的采用假设：销售愿意通过简短复盘与审核换取更好的跟进材料。真实工作负担要测量，不能仅因“对业务有好处”就假设会使用。

03 / 演示主案例建议 6 分钟，含操作

两个候选，三个仍需讨论的问题。

虚构演示案例 · 不是已发生的客户或成交结果

Evan 和 Mia 试驾后考虑两套 Model Y 配置。Evan 关注续航与驾驶体验，Mia 关注后排长途舒适度；家庭希望月供约 ¥4,000，目前没有家充，常用区域尚未确认。

  1. 先归属，再记录

    销售选择客户及本次会话，在真实官网分别配置并 Capture 两个候选。实际试驾车型另行确认，不能用第一候选代替。

  2. 自然补充，手动发送

    粘贴必要信息或口述复盘；检查实时字幕后发送。语音是输入方式，不自动把转写内容当成确认事实。

  3. 确认会影响判断的疑点

    如果转写出现与原预算不一致的金额，先确认；充电查询缺区域，询问常用区域或地铁站，不要求精确门牌。

  4. 按需准备，审核后交付

    条件充分时查询、计算并生成草稿；不足时保留缺失。销售审核重点结论与待确认事项，发布固定 Report 链接。

客户最终应该带走什么

正在比较：两套真实候选方案及各自代价。
已经确认：本次有依据的体验反馈和预算。
仍需确认：无家充的日常便利性，以及 Mia 的后排长途体验。

当前真实模型、语音识别和地图尚缺配置。主流程可在显式 Mock 界面讲解交互；真实采集单独展示，不把两者混称完整真实闭环。

04 / Agent 的必要性与边界建议 5 分钟

价值在于判断下一步，而不只是写报告。

相同的“生成报告”意图，可能需要不同动作。先检查已知信息与冲突，再选择工具；工具返回结果后重新判断是否足够，不要求每位客户都完整跑一遍地图、金融和成本。

销售提出目标 + 本次客户、候选和已确认信息
↓
存在关键冲突

预算、价格或归属不一致 → 停下来确认；未解决前不发布。

缺必要条件

如缺充电区域 → 追问；销售暂不清楚则保留未知，不猜测便利性。

条件已充分

选择所需查询 / 确定性计算 → 读取实际结果 → 决定补查或准备草稿。

↓
有来源的结果 / 明确的缺失 → 销售审核 → 手动发布

静态决策示意，不是实时运行日志。局部失败保留已完成内容；达到运行限制时明确停止，由销售决定是否继续。

模型负责什么

理解目标、提取待确认信息、选择必要工具、根据观察继续判断、组织可读总结。

工具负责什么

读取来源、查询站点、计算金融和能源成本。金额由确定性计算产生，不让模型凭记忆生成当前价格、利率或节省金额。

人负责什么

确认事实冲突、补充未知业务信息、审核措辞与结论、决定发布。普通聊天指令不能绕过审核自动发给客户。

例外如何影响客户结果
  • 地图失败：显示该模块缺失，不写“没有家充也很方便”。
  • 能源假设不全：省略节省金额与曲线，不为凑图补默认事实；能源成本不等于总持有成本。
  • 输入发生变化：旧计算与草稿标为待更新，重新审核；已发布旧链接保持原内容与来源时间。
  • 转写中断：保留已收到文字，销售可纠正或重说；不自动发送。
  • 客户“看过资料”不等于“顾虑已解决”，更不能推断购买意愿。
05 / 未来上线的验证设计建议 4 分钟

证明增量，需要一个可信的对照。

核心问题：如果没有 Tess，同一类客户原本会有多少人下定？

拟在可比门店与销售团队中分层随机分组：实验组在现有服务基础上使用 Tess，对照组保持现有服务。按团队分组减少销售把 Tess 的追问方法带入对照组的影响；需要足够多的独立团队，并按团队聚类分析。

主要结果

固定观察期内的有效下定率。分母为最初分组、符合条件且试驾时尚未下定的独立购车客户，不只算收到或打开 Report 的人；重复试驾不重复计入。

订单与归因

关联实验分组、客户、试驾和 CRM / 订单结果。同期开跑以减少价格活动与季节变化影响；提前约定订单取消、观察起点和观察期。

解释机制

观察信息整理与审核耗时、采用覆盖、未决事项是否经明确确认得到处理。打开率与问答次数只说明使用，不能直接代表转化。

代价与长期结果

同时看事实错误、投诉、隐私问题、销售总投入及取消率。更长观察期若差异消失，可能是提前成交，而不是新增成交。

实施前还缺：历史下定基线、客户决策周期、团队间差异，以及业务上值得识别的最小提升。据此估算样本量与试验周期，预先固定分析规则；目前没有转化提升结果。

如何区分报告本身与 Agent 的贡献

第一轮验证整套 Tess 辅助服务。若有整体增量，再比较“结构化静态报告”与“相同报告加 Agent 按需分析 / 持续互动”。不能将整套服务的提升直接归因给模型或 Agent。

先做小规模可用性与流程试点，检查准确性和使用负担，再进入足够样本的随机对照；Demo 只证明部分技术与体验可行性。

哪些已验证，哪些仍待验证。

独立验证通过

已在 Tesla 中国 Model Y 真实配置器和已安装的采集插件中独立验证两套配置变化、金融可见字段和旧快照保持；无需制作 Mock 官网。此证据属于 Capture 可行性阶段，不等于最终插件全部业务验收完成。

阶段验证通过

内部业务与交互
Mock / 静态

销售身份、内部 CRM / 金融能力和后续客户事件采用 Mock。用户侧问答、分享、联系与预约仅静态展示；没有实际订单或支付。
